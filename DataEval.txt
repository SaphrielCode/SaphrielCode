1. BENCHMARK MODEL FAMILY
Use the same implementation and architectural choices across candidates:
- Decoder-only, causal self-attention; no access to future tokens.
- Pre-normalization with RMSNorm and rotary positional embeddings.
- Standard multi-head attention, with 32 dimensions per head.
- Production feed-forward: SwiGLU with separate input and gate projections (192 to512), SiLU on the gate, elementwise multiplication, and output projection (512 to192). No biases.
- Historical comparison models may explicitly use two-matrix GELU feed-forward blocks; do not infer the production architecture from those legacy defaults.
- No linear biases and no dropout for this initial benchmark.
- Tie the token embedding and output projection weights. Count shared weights once.
- Vocabulary: exactly 8,192 entries, including special tokens.
- All trainable parameters, embeddings and normalization weights count toward the reported model size.

Starting candidates (benchmark configurations, not a final production commitment):
  Candidate A (production): 8 layers, width 192, 6 attention heads, SwiGLU intermediate width 512.
  Candidate B (historical alternative): 10 layers, width 256, 8 attention heads, GELU intermediate width 1,024.

With one embedding table, two RMSNorm vectors per block, one final RMSNorm vector, and no other learned parameters:
  SwiGLU parameter count = vocabulary * width + layers * (4 * width^2 + 3 * width * ff_width + 2 * width) + width.
  GELU comparison count = vocabulary * width + layers * (4 * width^2 + 2 * width * ff_width + 2 * width) + width.
  For production ff_width=512 at width192, the block matrix term remains12 * width^2, matching the former GELU width768 count.
  Candidate A: 5,115,072 parameters, approximately 5.1M.
  Candidate B: 9,966,848 parameters, approximately 10.0M.
The implementation must print its actual unique trainable parameter count and reconcile any difference before comparing runs.

Initialization and reproducibility:
- Initialize from scratch in FP32 on CPU. Do not load pretrained weights.
- Use a recorded initialization rule rather than framework defaults: token embeddings and attention/feed-forward matrix weights are independent normal samples with mean 0 and standard deviation 0.02, except the two residual-output projections in each block.
- Initialize each attention output projection and feed-forward output projection with standard deviation 0.02 / sqrt(2 * number_of_layers). SwiGLU input and gate projections each use standard deviation0.02. Preserve the tested initialization order: qkv, attention output, FF input, FF output, then FF gate per block. This is a chosen starting rule, not a guarantee of training stability.
- Initialize every RMSNorm scale to 1. There are no trainable bias vectors. Rotary position values are deterministic, not randomly initialized; fix RoPE theta at 10,000 for both candidates.
- The tied output head shares the embedding parameter object and is not initialized independently. Verify both sharing and the unique parameter count.
- Performance-screening model initialization seed: 42. Training-data order seed: 43, independent of the initialization RNG. Record Python, numerical-library and framework RNG seeds, software versions and initialization implementation/version.
- Save or hash the initial state for each architecture. Verify that all fresh-process repeats of that architecture begin with identical parameter values, regardless of batch size or thread count. Different-sized models are not expected to have matching tensors.
- For later learning experiments, predeclare multiple initialization seeds and pair each baseline/auxiliary comparison by seed and initial shared-model weights. Give generator/corruption RNGs separate recorded seeds.

2. INITIAL TRAINING SETTINGS
- CPU execution, FP32 parameters and arithmetic, without automatic mixed precision.
- AdamW: learning rate 0.0003, betas (0.9, 0.95), epsilon 1e-8.
- Weight decay 0.1 on matrix weights; exclude normalization vectors.
- Global gradient-norm clipping at 1.0.
- Fixed learning rate for the short performance benchmark. A longer training schedule is a separate decision.
- Cross-entropy over valid next-token targets, excluding padding.
- For each training update, sum the unreduced next-token negative log-likelihood over valid targets and divide by that update's valid target-token count. Padding/ignored labels contribute neither loss nor count. An update with zero valid targets is invalid and must not divide by zero.
- Validation/test loss = total negative log-likelihood over all valid target tokens / total valid target-token count over the entire evaluated split. Do not average batch means, sequence means or per-document means without token weighting.
- Accumulate detached evaluation loss sums in float64, with an integer valid-token count; evaluate with gradients disabled and the model in evaluation mode. Report the numerator, denominator, natural-log loss in nats/token and the fixed target-selection/masking rule. If reporting perplexity, use exp(aggregate loss) and flag overflow.
- Keep evaluated documents and target selection fixed across comparisons, and state how context length changes conditioning/packing. If reporting aggregate training loss, use the same token-weighted sum/count rule; keep it separate from the mean used for each optimizer update.
- Complete step: clear gradients, forward pass, loss, backward pass, gradient clipping, optimizer update.
- No gradient accumulation initially. Batch size means actual sequences processed in each optimizer update.
- Use an explicitly recorded AdamW implementation. Start with foreach=False and fused=False to establish a simple baseline.
- Eager execution initially; compilation and other optimizations require separately measured comparisons.

FP32 parameters, gradients and two Adam moment buffers alone require roughly 16 bytes per parameter: about 82 MB for A and 159 MB for B, in decimal units. This is an estimate of these buffers only, not total process RAM. Activations, logits, optimizer temporaries, framework libraries, data and allocator overhead must be measured separately through actual process memory.

3B. WINDOW AND BATCH CONFIGURATION
- Freeze vocabulary, special IDs, tokenizer configuration, backend version and hash in data/TinyStoriesBatches128_Unigram8192/tokenizer-lock.json.
- Corpus preparation converts newlines and strips outer whitespace before tokenization. The tokenizer itself applies NFC only.
- Verify encode/decode behavior, unseen Unicode handling, split isolation, future/padding leakage, target coverage, deterministic initialization, weight sharing and token-weighted loss.

Window policy: document-isolated-right-pad-v1.
- A window has 128 input positions and 128 next-token target positions, and belongs to exactly one story.
- Treat every body token and EOS as a target exactly once per corpus pass. Use BOS as the first story input; later windows begin with the immediately preceding token from that same story. BOS is never a target.
- Chunk attention/RoPE positions restart at zero. No cross-story attention is permitted; histories before each new chunk are not cached or carried beyond its preceding input token.
- Pad short final windows on the right with ID 0. Convert target padding to ignore_index=-100 at load time. Valid causal queries cannot attend later padding; padded query outputs contribute no loss.
- Training window order is a frozen seed-43 permutation. Batch 1 and batch 4 group the same rows without duplicating them. Emit a smaller final batch rather than dropping targets.
- Updates per epoch = ceil(window_count / batch_size); all saved source tokens must be valid targets once per epoch.

- Store x/y as little-endian uint16; row metadata records story ID, target start and valid length. Preserve original document offsets.
- Count valid targets for loss/throughput and padded positions for executed dense-matrix work.
- Verify selected source integrity and batch locks with tools/verify_batches.py --tokenizer-kind unigram --vocab-size 8192 before each run. Prepared output directories must refuse overwrite.
- Future timed runs must start from the declared initialization, without silently continuing pilot weights.
